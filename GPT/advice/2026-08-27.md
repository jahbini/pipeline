# 2026-08-27 — Qwen3.5-27B RAM-bound on mac-mini; UI write-path model-guard fix; pipes/ ignored end-to-end

## 21:15 UTC — Qwen3.5-27B on mac-mini is RAM-bound, not code-bound

**Context**: Followed up on the 2026-08-26 open item "verify Qwen3.5-27B
end-to-end on mac-mini." Launched `chat_llm` on pipe `qwen3.8` (model
`mlx-community/Qwen3.8-27B-4bit`) via the UI. Sanitize logged cleanly:
1847 keys canonicalized (`language_model.model.*` → `model.language_model.*`),
333 mtp/visual dropped, 48 A_log renamed, 160 zero-centered norms folded,
0 conv1d transposes (community 4-bit dump is pre-transposed). Weights
loaded into unified memory (~15 GB). Runner then sat in `mlx::core::eval_impl`
with the MLX scheduler thread also idle-waiting.

At 24 min elapsed, still no generated token. Diagnostics:

- `hw.memsize = 17,179,869,184` (16 GB mac-mini, Mac16,10)
- `vm.swapusage`: 5.7 GB used of 7 GB swap
- Compressor holding ~8.5 GB compressed pages
- 16.9 M compressions / 14.7 M decompressions / 3.4 M pageins over lifetime
- Disk I/O over the run: 249 GB read / 222 GB written
- Runner CPU cycled 0–10 % — stalled on paging, not on compute

Killed the run; swap dropped from 5.7 GB → 759 MB, confirming the runner
was the swap pinner.

**Recommendation**: Mark 27B as **"code verified through sanitize + weight
load; decode requires a 32 GB+ Apple Silicon host to run at usable speed."**
Do NOT retry 27B on this mac-mini — the throughput floor with swap
thrashing on every DeltaNet forward pass will be << 1 tok/s and can pin
the machine for hours per prompt.

If you want to exercise the deeper-layer path (>32 layers) without
needing a 32 GB machine, pull Qwen3.5-8B or -14B and re-run the same
`chat_llm` recipe. 8B @ 4-bit lands around 5 GB and fits comfortably.

**Why**: MLX unified-memory allocations get compressed/paged like any
other anonymous memory once the working set exceeds RAM. A DeltaNet
recurrence step touches all 64 layers of weights per token, so every
per-token forward triggers page-ins across the full 15 GB set — the
worst possible access pattern for a swap-bound machine.

**How to verify**: on a 32 GB+ host, `sync-to-mini.sh`-equivalent the
current code, run the `qwen3.8` pipe's `chat_llm` recipe with the
prompt already staged in `pipes/qwen3.8/override/chat_llm.yaml`. Success
signal: `out/chat.txt` contains coherent English, and `chat_meta.json`
reports `tok_per_sec` on the order of 1–3 tok/s (expected — dispatch-
overhead-bound × 64 layers). Failure signal identical to what we saw
today (24+ min silent hang) means either the target host is also
under-RAM, or something has regressed in the DeltaNet path since 08-26.

## 22:00 UTC — UI "Write Override" was silently corrupting run.model on `<org>_<model>` pipes

**Context**: Reported symptom on mac-mini pipe `q35_4`, recipe
`chat_llm`: every "Write Override" click produced
`pipes/q35_4/override/chat_llm.yaml` with `run.model: q35/4` — the pipe
name mis-split at the first underscore, then merged over the correct
`Qwen/Qwen3.5-4B` from the legacy `override.yaml`. Same class of bug
the 2026-08-26 note said was fixed in `readOverride`, but the write
path was missed.

The fault lived in `writeControlOverrideText` (`writer/ui_server.coffee`
~line 1169). It called `inferModelIdFromPipeName(pipeName)` without
first checking whether legacy `override.yaml` already had `run.model`.
The 08-26 fix put that guard inside the read path but did not put it
inside the helper — so any future caller could reintroduce the same bug.

**Recommendation**: **Folded the guard into `inferModelIdFromPipeName`
itself** (done and deployed live to mac-mini). The helper now reads
`readLegacyOverride()` internally and short-circuits to `''` whenever
the legacy file already pins `run.model`. Both call sites (`readOverride`
and `writeControlOverrideText`) collapsed to a bare
`inferModelIdFromPipeName(pipeName)` call. Any future caller inherits
the guard automatically.

**Why**: The pipe-name split is a heuristic ("<org>_<model>" → "<org>/<model>")
that's only correct when the pipe was named following that convention
AND no legacy override exists. Pipes created via `/api/create_pipe` or
`bin/pipe-new.sh` always have a legacy `run.model`, so the inference
is never wanted for them. Putting the guard in the helper — not at
each call site — makes the safe path the only path.

**How to verify**: on `q35_4`, click Write Override in the UI (or POST
`/api/human_override`). Check `pipes/q35_4/override/chat_llm.yaml` —
it should contain only what you wrote, with **no `run.model:` line at
all** (legacy `override.yaml` supplies it via the runner's deep-merge).
Confirmed live on mac-mini after `sync-to-mini.sh` + UI restart.

Also spot-audited every other pipe-name→model inference site to be sure:
`handleCreatePipe` and `bin/pipe-new.sh` both take `model` as an explicit
input and write it verbatim (no inference); the runner and step scripts
never do pipe-name inference. Only the two `ui_server.coffee` call sites
were ever exposed to this bug class, and both are now covered.

## 22:30 UTC — `pipes/*` is fully ignored; canonical pipe list needs a home

**Context**: Mr. Hinds removed `pipes/*` from the writer repo because
runtime writes inside pipes were causing constant conflict with
pull/stash/rebase across laptop + mac-mini. `.gitignore` now excludes
the whole tree. We audited every file that lives under `pipes/<name>/`
and confirmed none of them need to survive in git — every one is
either regenerable from `bin/pipe-new.sh` (identity), derived per-run
(state, out, params, experiment, pipeline.json, logs), or too large /
too binary / too machine-specific to sync via git (`runtime.sqlite*`,
`env/`, `build/`).

Consequence: a fresh clone no longer knows which pipes exist or what
model each one uses. The information hasn't been lost — it lives in
Mr. Hinds' head and on the mac-mini's disk — but it needs a durable
home if we want another machine (or a wiped clone) to reconstruct the
working set.

**Recommendation**: Add a committed shell script `writer/bin/pipes-init.sh`
that runs `./bin/pipe-new.sh <name> <model> <pipeline>` for each
canonical pipe. Round-trips cleanly: deleting a pipe dir and re-running
the script reproduces its identity exactly. Executable documentation
of "what pipes exist and why," in the format we already use for
creation.

Current live pipes on mac-mini (2026-08-27):

- `q35_4` — `Qwen/Qwen3.5-4B` — default pipeline `reset` (chat_llm-focused)
- `qwen3.8` — `mlx-community/Qwen3.8-27B-4bit` — default `reset`
  (RAM-bound on this machine — see 21:15 entry)
- `Huihui-Qwen3-4B-Instruct-2507-abliterated` — `huihui-ai/Huihui-Qwen3-4B-Instruct-2507-abliterated`
- `sample`, `small`, `story` — legacy/scratch; confirm before including

Do not include the runtime SQLite in git even for a canonical pipe — if
you want to sync KAG state across machines, do it out-of-band with
`scp`/`rsync`, and note the sync procedure in `GPT/mac-mini-sync.md`.

**Why**: The alternative to a committed init script is either
(a) recreate pipes by hand on every fresh clone (fragile, undocumented,
loses the `pipeline` field of each), or (b) commit a subset of pipe
state files (which puts us right back into the pull/stash conflict
problem we just left). A shell script sidesteps both: version-controlled
identity, zero runtime state.

**How to verify**: on a fresh clone (or after `rm -rf pipes/*`), run
`./bin/pipes-init.sh`. Result: `pipes/<name>/override.yaml` and
`pipes/<name>/override/<pipeline>.yaml` present for each pipe, each
pinning the correct model. UI should list all pipes on `/api/status`.
No pipeline runs required — pipe *identity* is what we're proving.
